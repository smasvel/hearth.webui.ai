Which Ryzen AI model to pick — benchmarked live, not guessed: for a real ~470-token coding prompt, qwen3.6-moe-35b-a3b (MoE, only ~3B active params per token) measured ~9.6 tok/s decode after a ~9.2s time-to-first-token; the smaller dense qwen3.5-9b-npu had a much faster ~2.5s time-to-first-token but a slower ~5.7 tok/s decode — a dense model has to compute all 9B params per token, more than the 35B MoE model's active 3B. Counterintuitively, that makes the "smaller" model the slower one overall past ~90 completion tokens: at a 200-token reply the 35B finishes in ~30s vs the 9B's ~38s. So for actual code generation (functions, refactors — usually 100+ tokens), the 35B is the faster real choice; the 9B only wins for short replies/quick edits under ~90 tokens. QwenFLM06B (0.6B) is faster still at both ends but noticeably weaker at following coding instructions — treat it as a connectivity smoke-test model, not a coding one. Also confirmed live while investigating this: the NPU wasn't throttled or in a low-power mode — forcing turbo power mode (above the default performance) made zero measurable difference: this is the real hardware/kernel ceiling for each model, not a config issue.

defaultCompletionOptions.contextLength: 32768 on every chat entry above — added after a real report of Ryzen AI responses via Continue seeming shallow/not following the actual ask, root-caused directly: confirmed via the live API (both plain and through this exact Caddy LAN path) that the model reasons and follows multi-step instructions correctly when given a full prompt, so the problem wasn't the model. It was that Continue's config schema supports defaultCompletionOptions.contextLength to tell it how much context budget it has to work with — this field was missing from every entry here (LM Studio's too, not just Ryzen AI), so Continue likely fell back to a conservative built-in default and pre-truncated the system prompt/history/codebase context before ever sending the request, regardless of how capable the model actually is once it receives a full prompt. 32768 matches what both Lemonade models actually load with (confirmed live via GET /v1/health) and what this app already loads LM Studio models with by default.

Troubleshooting

OpenCode/Continue times out on the first request (then works)

Most common cause of a LAN timeout when the port is actually open: a cold model load. Ryzen AI (Lemonade) and vLLM each serve one chat model at a time — if your tool requests a model that isn't the one currently loaded, the server evicts the running model and loads the requested one before answering. On the NPU that can take ~a minute (measured live 2026-07-24: a 35B model cold-loaded in ~59s vs ~4s once warm), which is longer than the tool's default request timeout, so the first request times out — even though nothing is actually broken. The next request is fast because the model stays loaded.

This config avoids it automatically: the default "model" is now pinned to whatever chat model is currently loaded on this machine (see the Models panel), so your tool hits a warm model and answers immediately. Two things to know: (1) re-copy the config after you load a different model here, since the pinned default changes; (2) if you pick a different model in your tool's switcher, expect that one first request to take ~a minute while it loads (or pre-load it here first from the Models panel).

OpenCode/Continue chat silently never responds (no error at all)

From another machine on the LAN, check the firewall first — the actual root cause of a real remote client connection failure (2026-07-24): ufw on this machine allowed port 8443 but the 8444/8445 rules were never added when those proxies were created later, and ufw drops (not rejects) blocked connections, so the client hangs forever with no error — while every test run on this machine itself passes, because same-host traffic bypasses ufw entirely. That combination (works locally, silent hang from LAN, no error anywhere) is this. Diagnose from the other machine with curl -sk https://{{ help.lan_ip }}:{{ help.ports.lemonade }}/v1/models -H "Authorization: Bearer <token above>" -H "X-Hearth-Client: connectivity_test" — an immediate JSON reply means the port is open; a hang means firewall. Fix on this machine: sudo ufw allow 8444/tcp (and 8445/tcp), needs a password.

If the port responds but chat still hangs: the config's selected model no longer exists on the server it points at — most likely because your config predates the 2026-07-21 LM Studio chat-model deletion and still defaults to one of the deleted models (gemma-4-e4b, qwen/qwen3.5-9b, qwen/qwen3.6-35b-a3b via the lmstudio provider / port 8443). The server is up and reachable, so nothing fails at connect time — the request just asks for a model that isn't there, and the chat sits with no reply and no error. Confirmed from both a local client and a remote LAN client.

Fix: re-copy the current OpenCode config above (its default "model" now pins lemonade/qwen3.6-moe-35b-a3b, which is actually served), or in the model picker switch to any lemonade/… model. Verify what a server actually has before blaming config/TLS: curl -s https://{{ help.lan_ip }}:{{ help.ports.lemonade }}/v1/models -H "Authorization: Bearer <token above>" -H "X-Hearth-Client: connectivity_test" (8443 = LM Studio, currently embedding-only; 8444 = Ryzen AI, the real chat models; 8445 = vLLM, one model at a time). If the model you're selecting isn't in that list, no client-side setting can make it respond.

OpenCode/Continue file creation failing — a second NPU guard shim (2026-07-26)

Lemonade auto-loads a model on demand when a chat request names one that isn't loaded yet (the same just-in-time behavior LM Studio has). When that model is an flm-recipe (NPU) one, Lemonade starts its own independent copy of FastFlowLM's engine — completely separate from the standalone flm.service the tool-calling shim above sits in front of — and the two loaded at once can exceed this machine's RAM. Confirmed live: reproducing it OOM-killed flm.service outright, breaking whatever OpenCode/Continue request it was serving mid-generation — this is what "file creation keeps failing" traced back to. Caddy itself was never the problem; it was faithfully relaying a crashed backend's error.

Fix: a second small reverse-proxy shim (lemonade_guard_shim.py, its own lemonade-guard-shim.service on 127.0.0.1:13306) sits between Caddy's :{{ help.ports.lemonade }} and Lemonade's raw server: for any chat request naming an NPU model, it stops flm.service first, then forwards the request unmodified — every other request (embeddings, Whisper, Lemonade's own non-NPU chat models) passes straight through untouched. Caddy's :{{ help.ports.lemonade }} block now points at this shim instead of Lemonade directly. Verified live: manually reproduced the exact collision (it OOM-killed flm.service again), then confirmed the shim stops it cleanly beforehand and the same request completes with no crash.

"Context size has been exceeded" (400/500 error)

Agent-mode tool definitions plus whatever codebase context the tool includes (open files, etc.) can easily add up to more tokens than the model's currently *loaded* context window. The Models panel's Load now defaults every load to a 32768 context (and full GPU offload) automatically — LM Studio's own stock default is a much smaller 8192 regardless of the model's actual max, which is what causes this. If you still hit it with a very large agent preamble, unload the model and load it again with an even bigger value in "Load options → Context length". {% if is_admin %}From a terminal on this machine, the manual equivalent (which does not get either default automatically) is lms load <model-key> -c 32768 --gpu max.{% endif %} A bigger context window uses more RAM (mainly the KV cache, multiplied by the number of parallel request slots) — go bigger than you need, but not wildly so.

vLLM: a model Loads but never becomes ready (looks hung, RAM climbs)

Almost always a vision/multimodal model (an architecture with an image encoder, e.g. Qwen3.5-family checkpoints) — confirmed live (2026-07-23) that vLLM's CPU backend deadlocks forever trying to warm up the image encoder, repeating "No available shared memory broadcast block found" in journalctl every 60 seconds, indefinitely, regardless of model size or free RAM. Every Load already runs with --language-model-only to avoid this for models that don't strictly need multimodal support disabled, but a genuinely multimodal checkpoint simply can't be served by this backend right now — pick a text-only model instead, there's no config workaround for this one. {% if is_admin %}If RAM is climbing toward 90%+ while this happens, don't wait it out — systemctl --user stop vllm from a terminal on this machine frees it immediately; a manual stop won't trigger Restart=on-failure.{% endif %} Separately, a pre-flight check refuses to even attempt a Load for a model whose download size exceeds 65% of this machine's RAM, so a plain "too large" refusal at Load time is a different, unrelated (and much simpler) situation than this one.

vLLM: "502 Bad Gateway" through port 8445

The Caddy proxy itself is fine (a 502 means it authenticated your request and tried to forward it) — nothing is listening on localhost:8000 for it to forward *to*, meaning vllm.service isn't running. Most likely cause: every model was Unloaded from the Models panel and none has been Loaded since — unlike LM Studio/Lemonade, vLLM's "unloaded" state really is "the process isn't running at all" (see the Help panel's vLLM notes above), so Load a model there first. If a Load itself is failing/timing out, check from a terminal on this machine: systemctl --user status vllm and journalctl --user -u vllm -e (no sudo needed — it's a user-level service). {% if is_admin %}Settings page → "Test vLLM via Caddy" reproduces this same check without needing a terminal.{% endif %}
