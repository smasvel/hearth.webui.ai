Settings

Where this app reaches each backend, and the credentials it sends — shown in plain text since this page is already admin-only. Overrides here take effect immediately (no restart) and persist across restarts — clear a field to fall back to whatever .env has (or nothing, if .env doesn't set it either).

LM Studio

Ryzen AI (Lemonade)

Applied per-request (Lemonade's own model-load API silently ignores this setting, confirmed live) — covers both Hearth's own chat and OpenCode's config (extraBody). Turning this off skips the model's reasoning phase but does not meaningfully speed up a response dominated by prompt-processing time on a large context — it only removes visibility into what the model is doing. Ignored by models/templates that don't support it.

vLLM

vLLM itself has no runtime load/unload API — a vllm serve process only ever serves the one model it was started with. This app builds Load/Unload/Download/Delete on top of that anyway (Models and Downloads pages, same as LM Studio/Lemonade) by controlling a user-level systemd unit (vllm.service, no sudo needed) behind the scenes — Load rewrites its config and restarts it with the new model. Runs locally on this machine, CPU-only — this iGPU isn't a supported vLLM/ROCm target, so no GPU offload is used. Before Load ever touches the service, a pre-flight check refuses models whose download size exceeds 65% of this machine's RAM (raised from an earlier, too generous 80% after a real incident where a model that passed at 80% still hung the whole system under swap pressure once its KV cache came in) — you'll get a clear refusal instead of a stuck/crash-looping load.

Text-only models only. Every load always runs with --language-model-only (disables all multimodal inputs), because this app never sends images to vLLM and because a real incident (2026-07-23) showed vLLM's CPU backend hangs forever — not crashes, an actual deadlock — trying to warm up a multimodal image encoder, regardless of model size or available RAM. If a model you Load never becomes ready and just sits there, check whether it's a vision/multimodal architecture (e.g. Qwen3.5-family models with an image encoder) — that's the likely cause, and there's currently no workaround short of picking a text-only model.

SGLang — GLM-5.2 (remote)

Connects Hearth to an externally managed SGLang OpenAI server. GLM-5.2 is a multi-GPU-class model, so Hearth discovers and chats with the model already running at this endpoint; download, load, unload, and deletion stay with the SGLang host. Launch that host with a GLM-compatible reasoning and tool parser, then enter its base URL here (normally port 30000).

KoboldCPP

A llama.cpp GGUF server that serves one model at a time. Like vLLM it has no runtime load API — this app builds Load/Unload/Download/Delete on top by controlling a user-level systemd unit (kobold.service, no sudo).

GPU offload (Vulkan) & speculative decoding (2026-07-27): applies on the next Load, not live to whatever's currently running. GPU layers offloads to this machine's iGPU via Vulkan (try a high number like 99 for "all layers"; leave blank for CPU-only). A draft model must share the exact same tokenizer/vocab size as whichever model you Load next, or speculative decoding silently malfunctions — pairing models from the same family/release (e.g. Qwen3-8B with Qwen3-0.6B) is the safe way to guarantee that; matching-sounding names across different releases (e.g. Qwen2.5-Coder's 7B vs. its own 0.5B) are not guaranteed to match. Measured live on this machine: a matched pair gave a real but modest ~18% speedup over plain GPU decode (83% draft-token acceptance) — worth it, not a silver bullet.

FastFlowLM (Ryzen AI NPU)

The Ryzen AI NPU runtime run standalone (flm serve). It shares the NPU with Lemonade — only one can hold it at a time, so loading a FastFlowLM model frees Lemonade's NPU model first (and vice-versa). Runs as a system unit (flm.service) since the NPU needs raised memlock; this app starts/stops it via a passwordless polkit rule.

Default LAN model (OpenCode)

Which model OpenCode's generated config (Help page) defaults to, grouped by serving backend. Each option also shows the compute path reported by that backend; choose an option marked NPU for full NPU inference (a model name ending in “NPU” does not guarantee that its installed recipe uses the NPU). "Auto" picks whatever's already loaded, falling back to the Ryzen AI NPU model — good for a quick warm start, but the NPU is slow enough (~5 tok/s) that a large coding turn can outlast OpenCode's own client-side timeout and look like it "didn't respond." Pin a specific faster backend here instead if that keeps happening; this only changes the default — every model is still listed and selectable in OpenCode/Continue's config either way.

Web search and research

Controls when Hearth may search and whether it may open result pages. Relevance filtering, sponsored-result rejection, and advertisement blocking are always enforced. Disabling browser access still permits safe search-result snippets.

Set pages to 0 for snippet-only research. Direct URLs are opened only when both direct URLs and Playwright are enabled.

Tailscale

A second reachability path alongside the LAN, for a device that's on this machine's Tailscale tailnet — same Caddy ports, same bearer tokens, same CA cert, just a different IP. The Help page's LAN config always stays LAN; when this is on, it also shows a second, independent Continue/OpenCode config pair pre-built with the Tailscale IP — both are shown together, nothing gets replaced. See the Help page for the full DNS links for the browser app and certificate download. Backend API configs use the numeric Tailscale IP on their Caddy ports.

Chat request limits

Ceilings the app enforces on Hearth's own chat requests. A request that doesn't ask for a specific max_tokens uses Default max tokens, which ships set to the cap. Clear a field to restore its built-in default. These do not affect OpenCode/Continue, which talk to the backends directly.

OpenCode compaction

Baked into the OpenCode config the Help page generates. When a session nears the model's context limit, OpenCode summarizes older conversation and keeps Keep tokens of recent turns beside the summary. On a small-context model the summarization request itself can overflow ("cannot be reduced further without losing the latest exchange") — lower Keep tokens to leave more room for the summary. Buffer starts automatic compaction earlier; leave it blank to use OpenCode's own default (10% of the model's limit).

OpenCode context

Also baked into the generated OpenCode config. When on (default), each model advertises the context its backend is actually loaded with, so OpenCode never builds a request larger than the server's real window — a real report had a model loaded in LM Studio at 8192 while the config claimed 32768, producing "request (29899 tokens) exceeds the available context size (8192 tokens)". Turn this off to always advertise the fixed per-backend defaults. Fallback context applies only to models whose real context can't be detected (e.g. not currently loaded); leave it blank to keep each backend's tuned default.

Caddy (LAN access)

Read-only — parsed live from /etc/caddy/Caddyfile (this app doesn't write to it; edit that file and reload Caddy yourself to change anything here). Same CA cert as the Help page's Continue/OpenCode configs; the token shown below is the general-purpose "lan" one (manual/ad-hoc use) — OpenCode and Continue each get their own dedicated token, embedded directly in their generated configs in the Help page, not shown here.

Tailscale (via Caddy)

Same checks as "Caddy (LAN access)" above, but through the Tailscale IP instead of localhost — confirms Caddy actually has a site block matching that address (save any manual IP override above first if auto-detection isn't finding one).
